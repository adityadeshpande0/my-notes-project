## What is an API?

An <Term id="api">**API**</Term> (Application Programming Interface) is a set of rules for how one
program can ask another program for something.

Think of a **restaurant**:

- **You** (the app) don't walk into the kitchen.
- You look at the **menu** (the API documentation: what you're allowed to ask for).
- You tell the **waiter** (the API) your order.
- The **kitchen** (the server and its database) prepares it.
- The waiter brings back your **food** (the data).

On the web, most APIs work over <Term id="http">**HTTP**</Term> (the same protocol your browser uses
to load websites), and they usually send data as **JSON** (article #7). These are often called
**REST APIs** or **web APIs**.

## Requests and responses

Every conversation with an API is a **request** (your app asks) and a **response** (the server
answers).

**A request has:**

- A **URL**: _where_ to send it.

  ```text
  https://api.chaicorner.dev/snacks?category=drink
  ```

  - `https://api.chaicorner.dev` is the server
  - `/snacks` is the <Term id="endpoint">**endpoint**</Term> (path): which thing you want
  - `?category=drink` is a **query parameter**: extra options, like filters
- A **method**: _what_ you want to do:

| Method          | Meaning                                                                      | Restaurant analogy           |
| --------------- | ---------------------------------------------------------------------------- | ---------------------------- |
| `GET`           | **Read** data                                                                | "Can I see the menu?"        |
| `POST`          | **Create** something new                                                     | "Add a new dish to my order" |
| `PUT` / `PATCH` | **Update** something (`PATCH` changes part of it, `PUT` replaces all of it) | "Make that less spicy"       |
| `DELETE`        | **Remove** something                                                         | "Cancel the samosa"          |

- **Headers**: extra information (like the data format, or a login token)
- A **body**: the data you're sending (for `POST`/`PUT`/`PATCH`), usually JSON

**A response has:**

- A <Term id="status-code">**status code**</Term>: a 3-digit number saying how it went
- **Headers**
- A **body**: the data, usually JSON

| Status                  | Meaning                 | Example                                                                                          |
| ----------------------- | ----------------------- | ------------------------------------------------------------------------------------------------ |
| **2xx** ✅ Success      | It worked               | `200 OK`, `201 Created`, `204 No Content`                                                        |
| **3xx** ↪️ Redirect     | Look somewhere else     | `301 Moved Permanently`                                                                          |
| **4xx** 🙋 Client error | **You** asked wrongly   | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `429 Too Many Requests` |
| **5xx** 🔥 Server error | **The server** broke    | `500 Internal Server Error`, `503 Service Unavailable`                                           |

## `fetch`: making requests from JavaScript

**`fetch`** is the browser's built-in function for making HTTP requests. It returns a **promise**,
so it fits perfectly with `async`/`await`:

```js
async function loadSnacks() {
  const response = await fetch('https://api.chaicorner.dev/snacks');
  const snacks = await response.json();
  console.log(snacks); // [{ id: 1, name: "Samosa", price: 20, ... }, ...]
}
```

Notice there are **two awaits**:

1. **`await fetch(url)`** waits for the server to **start replying**: the status code and headers.
   You get a **`Response`** object, but the body hasn't been read yet.
2. **`await response.json()`** waits for the **whole body** to arrive and parses the JSON into a
   JavaScript value (like `JSON.parse`, from article #7).

### ⚠️ The #1 fetch surprise: 404 is not an error!

`fetch` only **rejects** (throws) when the request **couldn't happen at all**: no internet, the
server is unreachable, or the request was blocked. If the server answers with **404** or **500**,
`fetch` considers that a successful _conversation_ (the server did reply) and **resolves
normally**.

So you must check **`response.ok`** yourself (it's `true` for status 200–299):

```js
async function loadSnack(id) {
  const response = await fetch(`https://api.chaicorner.dev/snacks/${id}`);

  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }

  return await response.json();
}
```

### Handling every outcome: loading, error, success

A real interface needs to show **what's happening** at every moment:

```js
async function showSnacks() {
  showLoading(); // ⏳ "Loading…"
  try {
    const response = await fetch('https://api.chaicorner.dev/snacks');
    if (!response.ok) throw new Error(`Server said ${response.status}`);
    const snacks = await response.json();
    showList(snacks); // ✅ show the data
  } catch (error) {
    showError(error.message); // ❌ "Something went wrong" plus a retry button
  } finally {
    hideLoading();
  }
}
```

The `try` block covers **all** the failure types at once: network failures (`fetch` rejects), bad
statuses (your `throw`) and broken JSON (`response.json()` rejects).

### Sending data: `POST`

To send data, pass a second argument with the **method**, a **header** saying it's JSON, and the
**body** converted to a JSON string:

```js
const response = await fetch('https://api.chaicorner.dev/snacks', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Kachori', price: 25, category: 'snack' }),
});

const created = await response.json(); // { id: 13, name: "Kachori", ... }
// response.status → 201 Created
```

### Cancelling and timeouts: `AbortController`

Sometimes you need to **cancel** a request: the user navigated away, typed a new search, or the
server is taking too long.

```js
const controller = new AbortController();
fetch(url, { signal: controller.signal });
controller.abort(); // the fetch rejects with an AbortError

// Give up after 5 seconds:
fetch(url, { signal: AbortSignal.timeout(5000) }); // rejects with a TimeoutError
```

### Query parameters, the safe way

Build query strings with **`URLSearchParams`**, so spaces and special characters are encoded
correctly:

```js
const params = new URLSearchParams({ q: 'masala chai', category: 'drink' });
fetch(`https://api.chaicorner.dev/snacks?${params}`);
// …/snacks?q=masala+chai&category=drink
```

## The full set: Create, Read, Update, Delete

Most apps do four things with data, often called <Term id="crud">**CRUD**</Term>, and each one maps
to an HTTP method:

| Action     | Method                         | Example                  |
| ---------- | ------------------------------ | ------------------------ |
| **C**reate | `POST /snacks`                 | Add a new snack          |
| **R**ead   | `GET /snacks`, `GET /snacks/3` | List all snacks, or get one |
| **U**pdate | `PATCH /snacks/3`              | Change its price         |
| **D**elete | `DELETE /snacks/3`             | Remove it                |

## Good habits (and important warnings)

- **Never put secret API keys in front-end code.** Anyone can open DevTools and read your JavaScript
  and its network requests. Secret keys belong on a **server** you control, which makes the call on
  your behalf.
- <Term id="cors">**CORS**</Term>: for security, a browser only lets your page read responses from
  **another website's** API if that server explicitly allows it. If it doesn't, you'll see a
  "blocked by CORS policy" error in the console (and `fetch` rejects with a `TypeError`). That isn't
  something you fix in your front-end code: the API's server has to allow it (or you go through
  your own server).
- **Respect rate limits.** Many APIs limit how many requests you can make (a `429 Too Many Requests`
  response). Debounce search boxes ([article #10](/javascript/events))!
- **Show the user what's happening:** a loading state, a friendly error with a **retry** button, and
  an empty state ("No snacks found").
- **In React,** fetch inside a `useEffect` and cancel the request in its cleanup. Bigger apps often
  use a data-fetching library (such as TanStack Query) that handles caching, retries and loading
  states for you. You'll meet these in the React track.

## Quick recap

- An **API** lets your app ask a server for data. Web APIs use **HTTP** and usually **JSON**.
- A **request** has a URL (endpoint plus query parameters), a **method** (`GET`, `POST`,
  `PUT`/`PATCH`, `DELETE`), headers and an optional body.
- A **response** has a **status code** (2xx success, 4xx your mistake, 5xx the server's), headers
  and a body.
- **`await fetch(url)`** gives you a `Response`, and **`await response.json()`** gives you the data.
  Two awaits!
- **`fetch` doesn't throw on 404/500.** Always check **`response.ok`**. It only rejects for network
  failures (and aborts).
- **Send data** with `method`, a JSON `Content-Type` header and `body: JSON.stringify(data)`.
- **Cancel** with `AbortController`, and set a **timeout** with `AbortSignal.timeout(ms)`.
- Always handle **loading**, **error** and **empty** states. Never expose secret keys. CORS is
  decided by the server.
